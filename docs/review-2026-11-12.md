# Trading-bot design reviews (12.11.2026, from session f0437b4b)

Paper money only. Copied from the closed chat "Paper trading LLM bot design review".

## Review 1: harsh, 4 parts

**1. Biggest flaws**
- **Unfair metric.** The 10% cap and 5 orders per run mean the bot starts mostly in cash, while buy-and-hold is 100% invested. In a rising market the bot loses just for holding cash. Over 4 weeks (~20 days) noise swamps any skill. Fix: add a do-nothing baseline and a random-orders bot, and compare against all three.
- **Fill timing.** The bot decides after the close, so filling at that same close uses information the bot could not have traded on. Fix: fill at the next day's open, and add a test for it. "Prices ≤1 day old" also fails every Monday (Friday's close is 3 days old, likely). Use a trading calendar instead.
- **Validation only checks each order alone.** It needs to check the portfolio state: the 10% cap on the total position, no selling shares you don't hold, no negative cash. Also log the full prompt, headlines, model name and raw output each day. Without that, a run can't be reproduced. Treat headlines as injection risk (likely): cap their length and count.

**2. Your assumptions**
- yfinance is an unofficial scraper, so it likely breaks or rate-limits now and then. Save each day's raw snapshot and use split-adjusted prices consistently.
- A 0.1% fee is fine (conservative, likely). Real costs on big US stocks are spread and slippage, not commission.
- LLM cost is likely cents per day for one call of a few thousand tokens. You can afford more calls.
- Freeze the watchlist before day 1. Choosing it now, knowing which stocks did well, is itself a leak.

**3. Simpler design.** Have the LLM predict next-day up or down per ticker with a confidence. Score it by hit rate and Brier score against "always up". That gives 10 predictions a day, ~200 in 4 weeks, instead of ~20 trades. Run it from GitHub Actions cron (likely free), so a sleeping Mac no longer matters. Add the simulator as v2.

**4. Verdict: build with changes.** Fix the benchmark and the fill timing first, and consider starting with the prediction-scoring version.

## Review 2: the scoring-bot draft (worst first)

| # | Problem | Why it matters | Proposed fix |
|---|---|---|---|
| 1 Leak | The base rate (past-year up-day share) and the momentum baseline can be computed at report time from a later snapshot. | The baseline then sees days after D, so it looks better than it was. | Compute each baseline on day D from the day-D snapshot only. Store it in the call row. Add a "truncate at D" test. |
| 2 Leak | "Safe to re-run" is unclear. A late or manual re-run after D+1 opens could call the LLM again with newer headlines and prices. | The call is then not a real forecast. | Refuse a new call if one exists for D, or if the time is past D+1's open (13:30 UTC). Store a call timestamp. A re-run only re-reads the stored call. |
| 3 Stats | The interval counts 10 calls a day as independent, but one market-wide move drives most of them. | The interval is far too narrow. Effective samples are likely ~2–3 per day. | Use day as the unit: the mean per-day difference vs the base rate, with a bootstrap over days. Report n_days. |
| 4 Stats | Time to a meaningful result. | 4 weeks is only ~20 days. A 5-point edge likely needs 1+ year. 2–3 points likely needs several years. | State this in the report. 4 weeks only shows whether the pipeline works. |
| 5 Baseline | "Always-up" is named wrongly. It is a base-rate forecaster. Its hit rate is the up-day share (~53%, likely), not 50%. | The LLM would look better than it is if compared to 50%. | Rename it `base_rate`. Compare hit rate to the base-rate hit rate and to 50%. |
| 6 Baseline | Momentum (12-month return > 0) is near "always up" in a bull market. It is binary, so it has no Brier score. | It adds little. If the LLM sees the 1-year closes, it is not independent either. | Cut it (see 12), or say what the LLM sees. |
| 7 Label | Scoring uses adjusted closes, but the question is "closes up". On an ex-dividend day a small price drop can score as "up". yfinance `Close` is likely already split-adjusted. | Label noise, and the question differs from what is scored. | Score on `Close`. Use adjusted only for the 1-year baselines. Define the p_up = 0.5 tie (exclude it). |
| 8 Stats | The calibration table has few calls per bucket. LLM p_up values likely cluster at 0.4–0.65. | It looks informative but is noise. | Use 3 buckets. Show n per bucket. Hide any bucket with n < 30. |
| 9 Failure | yfinance often gets rate-limited or blocked on cloud IPs (likely). A bar may be empty, partial or revised later. D is read at D and again at D+1. | Missing days, or a different D at call time and score time. | Retry with backoff. Log "no data" per ticker. Score each ticker alone. Store D as the LLM saw it. Add a fallback source (likely). |
| 10 Failure | A "no run" row cannot be written by a run that never happened. Cron can be delayed or dropped (likely). Public-repo schedules are likely paused after 60 days of inactivity. Two pushes can race. | Silent gaps. | The next run compares the dates in log.csv with the trading calendar and writes "no run" rows. Use `git pull --rebase` before pushing. Rely on failure emails. |
| 11 Failure | RSS can be empty or down, have missing or wrong dates, or contain injection text. Headlines are not per ticker. | The input varies between days. | Drop items with no timestamp. Log the headline count per day. Injection only skews p_up, since nothing can act. |
| 12 Cut | Candidates to cut or reduce: the momentum baseline, the daily 1-year snapshot, and `Adj Close` in the daily file. | They bloat the repo and add no insight. | Commit one day-0 history file, then only the new bar daily. Run headlines as a version ablation: prices-only v1, then headlines v2. |
| 13 Drift | The model alias may change silently, and temperature 0 is not fully deterministic (likely). | Scores mix different models. | Pin a dated model ID. Store the response ID. |
| 14 Tests | Missing tests: re-run after D+1 doesn't re-call the LLM; Friday→Monday and pre-holiday D+1; early-close day; duplicate ticker; p_up as a string or NaN; p_up = 0.5; markdown-fenced JSON; retry succeeds or fails; one ticker missing at D+1; partial live bar; ex-dividend label; RSS with no date or empty; newest-20 cut order; injection headline; push conflict; a hand-computed Brier value. | Each is a failure that would otherwise be silent. | Add them before the code. |

**Three changes first:**
1. Make each call write-once and time-boxed (rows 2 and 10). Store the baselines with the call, computed from the day-D snapshot only (row 1).
2. Score on `Close` with an explicit tie and flat rule. Make the day the unit for the interval, and rename the base-rate baseline (rows 3, 5 and 7).
3. Add yfinance resilience, per-ticker "no data" handling and "no run" detection (rows 9 and 10).
